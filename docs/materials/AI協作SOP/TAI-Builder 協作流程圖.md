# TAI-Builder 協作模型說明

（角色 × 文件 × AI × 審批 × 閉環）

---

## 一、核心概念

TAI-Builder 是一套「人類決策 × AI 執行」的開發協作模型：

* 人類負責：需求定義、設計決策、審批把關
* AI 負責：理解規格、執行開發、同步文件
* 文件同時服務「人」與「AI」，但格式不同

👉 最終透過文件回寫形成「閉環開發」

---

## 二、流程分段

### 設計篇（人主導）

1. 需求定義
2. 系統設計
3. 規格定義

### 實作篇（AI 主導）

4. 任務拆解
5. 程式開發
6. 文件回寫

---

## 三、流程 × 文件 × 角色 對照表（精簡版）

| 階段   | 角色（產出）  | AI文件（執行用）     | 傳統文件（審批用）      | 關鍵目的    |
| ---- | ------- | ------------- | -------------- | ------- |
| 需求定義 | PM      | proposal.md   | PRD            | 定義目標與範圍 |
| 系統設計 | SA / SD | design.md     | SRD / SDD      | 定義架構與技術 |
| 規格定義 | SA      | specs/        | FRD / UC / API | 定義精確規則  |
| 任務拆解 | PG + AI | tasks.md      | WBS            | 任務排序與拆解 |
| 程式開發 | AI      | Code + Test   | 程式碼 / 測試案例     | 完成功能    |
| 文件回寫 | AI + PG | blueprints.md | 設計文件 / 架構圖     | 同步系統現況  |

---

## 四、文件對應關係（完整版本）

| TAI 文件        | 對應傳統文件                | 說明        |
| ------------- | --------------------- | --------- |
| proposal.md   | PRD                   | 商業需求與目標   |
| design.md     | SRD / SDD             | 系統需求＋架構設計 |
| specs/        | FRD / UC / API / 資料字典 | 可執行規格     |
| tasks.md      | WBS                   | 任務拆解      |
| Code + Test   | 程式碼 / 測試案例            | 實際產出      |
| blueprints.md | 設計文件 / 架構圖            | 系統現況      |

---

## 五、AI 與人類的分工（關鍵）

### 人類（決策與審批）

* 看：PRD / SDD / API 文件
* 做：定義、審核、決策

### AI（理解與執行）

* 看：proposal / specs / tasks
* 做：生成、測試、同步

---

## 六、文件轉換流程（核心邏輯）

```text
PRD
↓
design.md（整合 SRD / SDD）
↓
specs（轉為可執行規格）
↓
tasks（轉為執行步驟）
↓
Code（系統實作）
↓
blueprints（回寫文件）
```

---

## 七、關卡（Gate）機制

每一階段必須通過審批才能往下：

1. 需求確認（Scope OK）
2. 架構審核（Architecture OK）
3. 規格凍結（Spec Freeze）
4. 任務啟動（Task Start）
5. 開發完成（Code OK）
6. 驗證完成（Verify OK）

---

## 八、閉環機制（Closed Loop）

當驗證不通過時：

🔁 回到以下階段修正

* specs（規格）
* tasks（任務）

👉 確保文件、程式、測試一致

---

## 九、關鍵轉變（導入重點）

1. 文件不只是「說明」
   → 變成「AI 可執行輸入」

2. specs 成為核心
   → 取代分散的 FRD / API 文件

3. 文件與程式同步
   → 透過 blueprints 自動更新

---

## 十、總結

傳統開發：
文件 → 人 → 程式（斷裂）

TAI-Builder：
文件 → AI → 程式 → 文件（閉環）

👉 實現：

* 可控開發
* 高品質交付
* 可持續優化
